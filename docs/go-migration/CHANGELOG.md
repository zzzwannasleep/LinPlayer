## v0.5 · 2026-08-30 · SPIKE-1a 结题(PGS/SUP × render API)

### 起因

项目负责人提出一条来自真实经历的反对意见:「之前写 Flutter 就是因为纹理导致 libmpv
一直显示不了 PGS/SUP 这类图形字幕」。**这条若成立,`SPEC.md` §7.3「默认赌 B」直接出局**
—— 图形字幕是蓝光原盘 / WEB-DL 的常态,而路径 A 的代价是 OSD 盖不上视频,
`UI_PC.md` §8 要整章重写。

### 结论:归因不成立,路径 B 未被排除 ✅

实测 6 个用例(含**自建纹理 FBO** + 真 H.264 + `d3d11va-copy` 硬解),
噪声基线**恒为 0**,字幕信号 2.2~2.8 万像素,差异区聚成 677×68 位于画面底部,
截图肉眼可辨认中英双行字幕。语料是真实 `.sup`(1359 条,1920×1080 画布)。

**交叉验证**:mpv 报的 `sub-start=532.823956 / sub-end=537.370167` 与自写 PGS 解析器
算出的该条逐位对上 —— 两个独立实现互证。

报告:[`spikes/SPIKE-1a-PGS-render-api.md`](spikes/SPIKE-1a-PGS-render-api.md),
复现脚本三个,已收进同目录。

### 顺带测出的新风险 R14 🔴

**桌面 WGL 上下文下,路径 B 拿不到 `d3d11va` 零拷贝**:
显式 `hwdec=d3d11va` **起不来**(回落软解),`auto` 最好只到 `d3d11va-copy`。

这与 `SPEC.md` §15.3 写的「Windows 默认 d3d11va 零拷贝是最佳档」**冲突** ——
那条结论来自现有 Rust 版,而它走的是路径 A(mpv 自己拥有窗口、自己建 D3D11 设备)。
已在 §15.3 加限定,并新增 TODO **S1.2b**:测 ANGLE 能否拿回零拷贝 + 量 `d3d11va-copy` 在 4K60 的代价。

### 当年 Flutter 为什么不显示(未证实)

从 git 历史取出当年实现,它建的是 **GLES 2.0** 上下文
(`EGL_CONTEXT_CLIENT_VERSION, 2` + `MPV_RENDER_API_TYPE_OPENGL_ES`),
而 mpv 的 GPU 渲染器面向 GLES 3.0+ 设计。**列为最可能原因,不写进 SPEC 当结论。**

### 实验方法本身的三个教训(已写进报告 §7)

1. mpv 事件号是 `START_FILE=6 / END_FILE=7 / FILE_LOADED=8` —— 第一版搞错,
   在文件没加载完就查属性,对照信息全是 `None`,结论不能用
2. **必须有负对照** —— 「开关字幕差 2 万像素」这个数字在没有噪声基线时什么都不证明
3. 大幅负 `sub-delay` 不要再叠 seek —— 叠了外挂字幕流跟不上,三个用例 S 全假 0,
   看起来像"硬解下 PGS 不显示"

## v0.6 · 2026-08-31 · SPIKE-1b 结题:推翻「默认赌 B」

### 起因

项目负责人:「路径 B 能不能保证 OSD 没问题的同时,编解码也是流畅的?
之前这两个是要取舍的,我不想取舍才换成 rust+react,现在也不想取舍。
我们的 OSD 不用 mpv 自己的 lua 脚本写。」

### 先纠正一个前提

**「漂亮 OSD」和「零拷贝硬解」本来就不在一条轴上。** 现有 Rust+React 版同时拿着两样 ——
做法是 **A2:mpv 独立顶层窗口在下、透明 UI 窗口在上**。只有 A1(子窗口 `--wid`)才逼你用
mpv 的 Lua OSD,而 A1 从来不是候选。**真正的轴是「几何对齐复杂度 vs 解码路径退化」。**

### 结论:Windows 上路径 B 要取舍,而且核显上 4K 播不了 🔴

| 场景(Intel UHD 770 核显) | 路径 A 零拷贝 | 路径 B `d3d11va-copy` |
|---|---|---|
| 1080p60 → 1080p | 推进 1.001 ✅ CPU **11%** | 推进 1.005 ✅ CPU **48%** |
| 4K60 → 1080p | 推进 0.998 ✅ CPU **7%** | 推进 **0.862 ❌** 渲染 **12.2 fps** |
| 4K60 → 4K | 推进 0.999 ✅ CPU **7%** | 推进 **0.924 ❌** 渲染 **14.2 fps** |

**核显是主场景不是边角料**(负责人:「要测试集显的,有些人可能不装显卡的」)。
路径 B 在核显上的 4K 是**播不了**,不是慢一点。

根因是结构性的:换 **ANGLE(EGL over D3D11)** 也拿不回零拷贝 ——
这个 mpv 里 `d3d11egl` 与 `EGL_ANGLE_d3d_texture_client_buffer` **一个都没有**
(现代 mpv 移除了 ANGLE),而 render API **只有 OpenGL / SW 两种类型,没有 D3D11 类型**。
判别器:同一个 libmpv、同一块卡,走路径 A 就能拿到 `d3d11va`。

### 新增方案 D:DirectComposition 视觉合成

mpv 用 `gpu-api=d3d11` 渲自己的 swapchain(零拷贝完整),Avalonia 走 `WinUIComposition`,
两个 visual 放进同一棵 DComp 树。**唯一可能同时拿到 单窗口 + 自绘 OSD + 零拷贝** 的方案。
现代浏览器做视频覆盖层就是这条路。**未验证,已立 S1.7,优先级高于 B。**

### 裁决顺序改为

```
1. 先做 D(DirectComposition)   <- 唯一可能三样全有
2. D 不通 -> 退 A2(双顶层窗口) <- 已在产验证,坑已知已记录
3. B 只在 Linux 上仍是候选       <- vaapi/nvdec 有成熟 GL 互操作,须单独实测
4. C 不进生产
```

## v0.7 · 2026-08-31 · 订正 v0.6 —— 路径 B 可用,代价是 CPU 不是可用性

### 本条订正上一版的错误结论

v0.6 写的「**核显上路径 B 的 4K 播不了(12~14 fps)**」**是错的**。
根因是测试台污染:我对一个摆在屏幕外的 1920×1080 窗口每帧做 `eglSwapBuffers`,
**那一步才是瓶颈**;另外开了 `ADVANCED_CONTROL` 却从没调
`mpv_render_context_report_swap()`,mpv 的帧率控制整个是瞎的。两处修掉后数据完全不同。

### 订正后的实测(Intel UHD 770 核显,输出 1920×1080)

| 场景 | A · 零拷贝 | A · copy-back | **B · render API** |
|---|---|---|---|
| **4K24**(真实影片帧率) | 满帧 · CPU **3%** | 满帧 · CPU **12%** | **满帧** · CPU 30%(含测试台开销) |
| **1080p60** | — | — | **满帧 60.0** · CPU **14%** |
| 4K60 | ~19 fps · 7% | ~15 fps · 19% | ~19 fps · 31% |

**4K60 是这块核显本身的天花板,不是 B 独有的** —— 零拷贝的 A 在同机同片下丢帧数相近
(407 vs 506)。实拍 4K 内容基本是 23.976/24/25 fps。

### 裁决:默认路径 B

零拷贝确实拿不到(只要渲染走 OpenGL 就跨 D3D11 设备边界,mpv 自己的
`gpu-context=win` / `dxinterop` 也一样),**但那是 CPU 代价不是可用性问题**,
换来的是消灭几何对齐的一整类 bug(现有约 1500 行窗口管理 + 历史故障高发区)。
**A2 永远是保底**,与 UI 框架无关。新增 **S1.10**:低端真机验 CPU 余量,不达标则退 A2。

### 方案 D(DirectComposition)已排除

libmpv 公开 API 给不出可被外部合成的 swapchain;`--d3d11-composition` 探测返回
option not found。**顺带澄清:Avalonia 的 `WinUIComposition` 不是 WinUI**,
是 Win32 后端的呈现模式(操作系统合成器 API)。**选 B 或 A2 都不需要碰 WinUI。**

### 另一处订正:根因写错了一版

v0.6 用「二进制里 `d3d11egl` 字符串 0 次命中」推出「现代 mpv 移除了 ANGLE」——
**这条证据不成立**(那是源文件名)。实际 `gpu-context=angle` 是合法取值。
真正的根因是**设备边界**:走 OpenGL 就跨了 D3D11 设备,只能 copy-back。

### 方法论

这一轮测试台出了 **5 次**问题,其中 2 次导致提交了错误结论,全部记进报告 §7。
共同教训:**性能测试里「测试台本身是不是瓶颈」必须先证伪** ——
判别器现成的:同一个 libmpv 用它自己的 VO 跑一遍,它快而我们慢,那慢的是我们的循环。

## v0.8 · 2026-08-31 · 路径 B 定案,契约随之改写

用户 2026-08-31 拍板:**做 B —— 单窗口 + 自绘 OSD,接受 CPU 代价**。

### 这个决定推翻了一段【一次做对】的契约

`§7.2` 原来只有一条视频通道(surface 句柄)。路径 B 下**桌面端根本没有 surface 句柄**,
只有 GL 上下文和 FBO。所以 §7.2 重写成**两条通道并存**:

| 平台 | 通道 | 理由 |
|---|---|---|
| Android / Apple | **A · surface 句柄** | `SurfaceView` / `CAMetalLayer` 是独立合成层,系统天然把 UI 画在视频上 |
| Windows / Linux | **B · GL 渲染** | 原生子窗口有 airspace 问题,只能让核心层渲进 UI 的 GL 场景 |

```c
lp_gl_init(get_proc_address, ctx)      // 建 render context
lp_gl_wants_redraw() -> int32          // 有没有新帧(暂停时返回 0,不白烧 GPU)
lp_gl_render(fbo, w, h, flip_y)        // 渲一帧
lp_gl_swapped()                        // ★ 上报上屏时刻,漏了帧率控制就瞎
lp_gl_uninit()                         // 解绑,阻塞返回
```

五条硬约束全部来自 SPIKE-1b 的实测,尤其:

- **`lp_gl_swapped()` 不许省** —— 漏了实测 4K60 从满帧掉到 18fps,
  而且**表现得像"架构性能不行"**,极难反查
- **一个进程只能有一条 GL 通道** —— 连开两条实测卡死 400 秒不返回
- **`lp_gl_uninit()` 必须阻塞**,返回后宿主才能销毁 GL 上下文

### §5.3「禁止传函数指针」开了唯一例外

`lp_gl_init` 的 `get_proc_address`。mpv 的 render API 强制要求它,没有替代方案。
例外的边界写死了:宿主拥有、不存进长生命周期结构、`lp_gl_uninit` 后立刻失效、
回调里不许调任何 `lp_*`。

## v0.12 · 2026-08-31 · SPIKE-2 结题(Windows/C#),契约被实测改了两处

报告:[`spikes/SPIKE-2-go-ffi.md`](spikes/SPIKE-2-go-ffi.md)。工程 `spikes/s2/`,可复跑,

### 🔴 契约改动一:光有 `defer recover()` 不够(§5.10)

**命令必须由 `lp_init` 时建好的 worker 池执行,不许在 cgo 调用里现开 goroutine。**

同一个 DLL、同一条命令,只改「故障是哪一类」和「goroutine 在哪儿创建」:

| 故障 | goroutine 在哪儿创建 | .NET 宿主 | Python 宿主 |
|---|---|:--:|:--:|
| 显式 `panic("…")` | cgo 调用里现开 | ✅ recover 住 | ✅ |
| **空指针解引用** | **cgo 调用里现开** | ❌ **`0xC0000409` 硬杀** | ✅ |
| 空指针解引用 | `lp_init` 时就存在的 | ✅ recover 住 | ✅ |

**死的时候什么都不打印** —— `GOTRACEBACK=system` 一个字没有,stderr 全空,只剩退出码。
试过无效的缓解:`DOTNET_LegacyExceptionHandling=1`、`debug.SetPanicOnFault(true)`。
**有效的只有 worker 池**,并有先绿后红的反向注入(`LP_INLINE_GOROUTINE=1`)钉住。

§5.10 的测试要求也补了:**必须把显式 panic 和运行时故障分成两条命令测** ——
只测前者会得到「recover 有效」的假结论,而真实世界的 panic 大多是后者。

### 🔴 契约改动二:内存判据不能用进程内存(§5.3)

第一版判据是「2 万次往返后进程私有内存增长 < 阈值」。反向注入(故意不 `lp_free`)之后:
**正常 23.7 MB,故意漏 24.5 MB —— 几乎一样**,漏掉的 C 字符串只有约 2 MB,
完全被 .NET 自己的分配淹没。

改成在核心层数 `alloc`/`free`:正常 **20020/20020/未释放 0**,注入后 **未释放 20020**。

> 这是「先红」纪律最典型的一次兑现:不注入,第一版那条判据会以
> 「红了但看起来只是阈值偏紧」的样子被调松,然后永远测不出真泄漏。

顺带排掉两个此前没验过的风险:**GOPROXY 可达**(拉 quickjs-go 成功)、
**quickjs-go 内嵌的 QuickJS C 源用项目级 zig cc 一次编过**(约 27s)。

### 🔴 三条写进 §9.2 的宿主约束(不写就偶发出错,而且错得像插件的锅)

| # | 约束 | 不做会怎样 |
|---|---|---|
| ① | 跑 JS 的线程必须 `runtime.LockOSThread()` | QuickJS 靠栈基址查栈溢出,Go 会把 goroutine 在 OS 线程间搬 → 误报 `RangeError: Maximum call stack size exceeded`。**锁线程 5/5 全绿,不锁 5/5 全败** |
| ② | 异步结果必须投回 JS 线程再造值 | 在非 owner goroutine 上 `NewObject()` 造的值无效,JS 侧拿到 `undefined` **且不报错**。`NewNull()` 这类常量不受影响 —— 所以 `ctx.sleep` 一直好的,一换成返回对象的 `ctx.http` 就坏 |
| ③ | 回调注册放 JS 侧 | `Value.Set` 接管引用而回调参数是**借来的** → 释放两次 → 段错误。quickjs-go 没有 `Dup` 可补 |

看门狗还有一条:中断处理器只在 JS **正在执行**时被调用,所以 `await` 期间不会误杀;
但 `await` 恢复后插件还要接着干活,**deadline 必须在每次泵作业时重置**。

### 两次「注入本身写错了」,比没注入更糟

- **② 号注入第一版**把死循环放在另一个 goroutine 上 Eval,违反 quickjs-go 的
  owner-goroutine 约束 —— 不但没测到东西,还**污染了后面所有测试**
  (S3.4 从通过变成失败)。改成开子进程才对。
- **③ 号注入第一版**里 `await` 完就 `return`,那段代码短到 QuickJS 的中断检查
  根本没触发,于是「不重置 deadline 也没事」—— **把一条真约束测成了不存在**。
  改成「等完之后接着干 300ms 的活」(真实插件的形状)才红。

> 这两次的共同教训:**注入必须忠实于真实形状。** 一个写错的注入会让你相信
> 护栏坏了,或者相信护栏不需要 —— 两个方向的错都比没有注入更贵。

### 还没做的

语料只有绿色包里带的 3 个,**不是「现存全部插件」**(S3.5);
只测了 `onEnable`,没测数据源的 `listDir`/`search`/`resolvePlay`(S3.6);
一个插件崩了之后同进程其它插件还能不能工作,没验(S3.7);性能一个数都没量。

## v0.14 · 2026-08-31 · SPIKE-5:弹幕机制成立,但观感待验

报告:[`spikes/SPIKE-5-osd-overlay-danmaku.md`](spikes/SPIKE-5-osd-overlay-danmaku.md)。
核心层实现在 `spikes/s2/lpcore/danmaku.go`,由 `AvaloniaProbe` 驱动并取证。

### 结论:`SPEC.md` §7.5 的选择不用推翻

Intel UHD 770 核显 / 4K24 / 输出 1920×1080,每档 12 秒 × 2 遍:

| 配置 | 渲染 fps | 丢帧 | CPU | **位置真变/秒** | 近白占比 |
|---|---:|---:|---:|---:|---:|
| 关弹幕(基线) | 24.0 | +0 | 21% | — | **0.00%** |
| **500 条弹幕** | **24.0** | **+0** | 30~36% | **18~19** | **7.9%** |
| 500 条 + `fps=60` 滤镜 | 21.9 | **+477** | 54~61% | 30~32 | 7.9% |

500 条弹幕下**满帧、丢帧 0**;近白像素占比从 **0.00% 跳到 7.9%** ——
基线正好是 0,这个 A/B 是决定性的。代价是 CPU **+9~15 个百分点**。

### 🔴 两条要写进规格的

1. **弹幕的平滑度被钉在约 19 次/秒**,而**不是**我们的循环不够快
   (循环转了 52.6 拍/秒)。原因:`\pos` 是从 `time-pos` 线性插出来的,
   而 **`time-pos` 只在视频帧边界更新** —— 24fps 片源上,推 60 次也只有 24 个不同位置。
2. **uosc_danmaku 的补救手段在核显上代价太大。** `vf append @danmaku:fps=fps=60`
   确实把平滑度抬到 30~32 次/秒,但**丢帧从 0 涨到 477**、渲染 fps 24.0 → 21.9、
   CPU 再 +25 点。**不能默认开。**

### 这条不是结题

**「19 次/秒对滚动弹幕够不够」是观感问题,数字答不了。**
`TODO.md` S5.2 要求的「录屏逐帧看」**没做**,S5.2 保持 `[~]` 而不是 `[x]`。
另外倍速、seek/暂停/换片、安卓真机、1080p60 片源、5 分钟长跑,全都没测。

### 一个量错对象的教训

第一版指标量的是「每拍推进的标准差」,得到 34ms(比均值还大),看起来像严重抖动 ——
其实那是 `time-pos` 在 24fps 片源上每 41.7ms 才变一次的**量化台阶**,不是抖动。
**量错了对象,会把一个正常现象读成故障。** 改成数「位置真的变了多少次」才看到真问题。
