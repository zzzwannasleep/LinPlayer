# SPIKE-1b · 路径 B 能不能在保住自绘 OSD 的同时保住零拷贝硬解

> 状态:**已结题(Windows 侧)**;Linux 侧未测
> 起止:2026-08-31
> 关联:`SPEC.md` §7.3、§15.3、风险 R14

## 1. 要回答的问题

项目负责人的原话:

> 「路径 B 能不能保证 OSD 没问题的同时,编解码也是流畅的?
> 因为在之前,这两个是要取舍的。我不想取舍才换成 rust+react,现在我也不想取舍。
> 我们的 OSD 不用 mpv 自己的 lua 脚本写,那很丑,也写不了好看的 UI。」

拆成两问:

- **Q1** 自绘 OSD 与零拷贝硬解,在路径 B 上能不能同时拿到?
- **Q2** 如果拿不到,退化后的解码还跑不跑得动 4K?

## 2. 先纠正一个前提:这两件事本来就不在一条轴上

**「漂亮 OSD」和「零拷贝硬解」不是互斥的 —— 现有的 Rust+React 版就同时拿着两样。**

它的做法是 **A2:mpv 独立顶层窗口在下,透明窗口在上画 UI**。
mpv 拥有自己的窗口和自己的 D3D11 设备,所以零拷贝完整;UI 是另一个顶层窗口,
所以想画多好看画多好看,**完全不碰 mpv 的 Lua OSD**。

所以真正的取舍轴是另一条:

| 方案 | 自绘 OSD | 零拷贝硬解 | 真实代价 |
|---|:--:|:--:|---|
| A1 子窗口 `--wid` | ❌ 盖不上 | ✅ | 只能用 mpv 的 Lua OSD —— **已被否决,不是候选** |
| **A2 双顶层窗口(现状)** | ✅ | ✅ | **手动几何对齐**:全屏白边 / z 序漂移 / wndproc 重入 / DPI 那一串 |
| **B render API → 纹理** | ✅ | ❌(见下) | 单窗口合成,但 Windows 上零拷贝拿不到 |
| C 软件回读 | ✅ | ❌ | 每帧全画面 CPU 拷贝 |

**A1 从来不是候选项。** 所以问题不是「OSD vs 性能」,而是
「**几何对齐的复杂度 vs 解码路径的退化**」。

## 3. 做法

同 SPIKE-1a 的环境(见那份报告 §3.1),另加:

| 项 | 值 |
|---|---|
| ANGLE | Tabby 自带的 x64 ANGLE(`libEGL.dll` / `libGLESv2.dll`),EGL 1.5,D3D11 后端 |
| 4K 语料 | 用 libmpv 自己 encode 的 **3840×2160 @60fps H.264**,20s / 148 MB |
| 输出分辨率 | **两条路径都是 1920×1080**(第一版 A 只有 960×540,4 倍像素差,那次数据作废) |

## 4. 实测数据

### 4.1 Q1:零拷贝在路径 B 上拿不到

先排除「是不是我们上下文配错了」。把 GL 上下文从 WGL 桌面 OpenGL 换成
**ANGLE(EGL over D3D11)** —— 也就是 mpv 官方在 Windows 上做 D3D11 互操作的那条路:

```
EGL 1.5  vendor = Google Inc. (Intel)
GL_RENDERER = ANGLE (Intel, Intel(R) UHD Graphics, Direct3D11 vs_5_0 ps_5_0)
ANGLE D3D 互操作扩展: EGL_ANGLE_d3d_share_handle_client_buffer,
                      EGL_ANGLE_d3d_texture_client_buffer
```

后端确实是 D3D11,互操作扩展也在。但:

| 上下文 | 请求 `hwdec` | 实得 `hwdec-current` |
|---|---|---|
| WGL 桌面 OpenGL | `d3d11va` | **`no`**(起不来,回落软解) |
| WGL 桌面 OpenGL | `auto` | `d3d11va-copy` |
| **ANGLE / GLES3** | `d3d11va` | **`no`** |
| **ANGLE / GLES3** | `auto` | **`d3d11va-copy`** |

#### 判别器:换成路径 A,同一个 libmpv、同一块卡、同一个片子

```
路径A  vo=gpu gpu-api=d3d11  请求 hwdec=d3d11va -> hwdec-current=d3d11va   ✅ 零拷贝
路径A  vo=gpu gpu-api=d3d11  请求 hwdec=auto    -> hwdec-current=d3d11va   ✅ 零拷贝
```

**所以不是构建的锅,也不是硬件的锅,是路径的锅。**

#### 根因

> ⚠️ **本小节的第一版结论「现代 mpv 移除了 ANGLE」是错的,已订正。**
> 当时的证据是二进制里 `d3d11egl` 字符串 0 次命中 —— 但那是**源文件名**,
> 本来就不一定出现在二进制里。**这条证据不成立。**

订正后的事实(用选项探测,比扫字符串可靠):

```
gpu-context=angle      -> 取值合法(mpv 的 choice 选项会校验,说明 ANGLE 上下文编译进来了)
gpu-context=dxinterop  -> 取值合法
gpu-context=angle 实跑 -> 初始化失败(libmpv 旁边没有 ANGLE 的 libEGL/libGLESv2)
gpu-context=dxinterop  -> 可用,但 hwdec-current 仍是 d3d11va-copy
gpu-context=win(WGL)  -> 可用,hwdec-current 仍是 d3d11va-copy
```

**所以:mpv 自己的 GL 系上下文也拿不到 d3d11va 零拷贝,只有 `gpu-api=d3d11` 拿得到。**
零拷贝要求解码器与渲染器共用同一个 D3D11 设备;走 GL(不论 WGL / dxinterop / 我们自己给的
ANGLE)都跨了设备边界,只能 copy-back。

> **Q1 的答案:Windows 上,只要渲染走 OpenGL(路径 B 必然如此),零拷贝就拿不到。**
> 这是设备边界决定的,不是某个构建的缺陷。

### 4.2 Q2:退化成 `d3d11va-copy` 之后还跑不跑得动

> ⚠️ **本节被改写过两次。** 第一版结论是「核显上 4K 播不了(12~14 fps)」——**那是错的**,
> 是测试台污染。踩坑记录见 §7,这里只放修正后的数据。

**全部跑在 Intel UHD 770 核显上 —— 这是主场景不是限定条件**(负责人 2026-08-31:
「要测试集显的,有些人可能不装显卡的」)。输出统一 1920×1080,每档跑 10~12 秒。

#### 4K24 —— 真实影片帧率(院线/流媒体 4K 基本是 23.976/24/25)

| 路径 | `hwdec-current` | 达成帧率 | 丢帧 | CPU(单核占比) |
|---|---|---|---:|---:|
| **A** · mpv 自有窗口 `gpu-api=d3d11` | **`d3d11va` 零拷贝** | 满帧 | 10 | **3%** |
| **A** · mpv 自有 GL 上下文 `gpu-context=win` | `d3d11va-copy` | 满帧 | 0 | **12%** |
| **B** · render API(WGL) | `d3d11va-copy` | **23.9 满帧** | 13 | 30% |
| **B** · render API(ANGLE) | `d3d11va-copy` | **24.1 满帧** | 10 | 36% |

#### 1080p60

| 路径 | 达成帧率 | CPU |
|---|---:|---:|
| **B** · render API(WGL) | **60.0 满帧** | **14%** |

#### 4K60

| 路径 | 达成帧率 | 丢帧(10s) | CPU |
|---|---:|---:|---:|
| A · 零拷贝 | ~19 fps | 407~415 | 7% |
| A · `d3d11va-copy` | ~15 fps | 456 | 19% |
| B · render API | ~19 fps | 506~511 | 31%(WGL)/ 61%(ANGLE) |

**读法:**

1. **路径 B 在核显上 1080p60 满帧、4K24 满帧。** 不是"播不了"。
2. **4K60 是这块核显本身的天花板,不是路径 B 独有的问题** ——
   **零拷贝的路径 A 在同机同片下丢帧数相近**(407 vs 506),两条路都只呈现约 15~19 fps。
   4K60 在实拍内容里是边缘场景。
3. **真正的代价是 CPU,不是能不能播。** 4K24:零拷贝 3%,copy-back 12%(mpv 自己的 GL VO)。
4. **B 那一栏的 30~36% 含测试台开销**:本脚本是 Python 忙轮询 + 渲进纹理 FBO + 无垂直同步。
   同样解码路径下 mpv 自己的 GL VO 只要 **12%** —— **真实实现的期望值应当接近 12%,不是 30%**。
   这一条是估计不是实测,标出来别当数据用。

### 4.3 关于 GPU 选择

**测试全程跑在 Intel UHD 770 核显上,不是这台机器上的 RTX 5060。**
这是**刻意保留的主场景**(项目负责人 2026-08-31:「要测试集显的,有些人可能不装显卡的」),
不是缺陷 —— 独显上的数字是另一个问题,不能用它替核显签字。

```
Get-CimInstance Win32_VideoController:
  Intel(R) UHD Graphics                (测试实际用的是这块)
  NVIDIA GeForce RTX 5060 Laptop GPU   (没用上)
```

Python 测试进程没有 `NvOptimusEnablement` 导出符号,也没设 Windows 的按应用 GPU 偏好,
所以落在了核显上 —— **这正好是风险 R10(双显卡没钉独显)的现场复现**。

独显上路径 B 大概率能跑住 4K60,但那不改变结论:

1. **目标机型本来就包含只有核显的机器** —— 对它们来说路径 B 的 4K 是不可用,不是"慢一点"
2. **零拷贝与否是结构差异,换块好卡只是把它盖住,不是消除它**
3. 独显笔记本平时也跑在核显上(见 R10:双显卡不钉独显就是核显),
   而**钉独显本身在 Linux 侧还没实现**

> **待补:** 同一套矩阵在独显上再跑一遍,拿到「路径 B 在 5060 上的 4K60 数字」。
> 需要把测试进程钉到独显(按应用 GPU 偏好或导出符号),本次没做。

## 5. 结论

### 5.1 直接回答

> **一半一半。**
>
> · **OSD:完全没问题。** 路径 B 的 UI 自由度是四个方案里最高的(单窗口内合成)。
> · **零拷贝:拿不到**,这是结构性的(见 §4.1),Windows 上无解。
> · **但退化后的解码仍然够用**:核显上 1080p60 满帧、4K24 满帧。
>   代价是 CPU 从 3% 涨到约 12%(同解码路径下 mpv 自有 VO 的实测值)。
>
> **所以这不是「不能用」,是「用 CPU 换掉几何对齐的一整类 bug」。**

### 5.2 但「不取舍」是有方案的,而且不止一个

| # | 方案 | 自绘 OSD | 零拷贝 | 单窗口 | 核显 4K24 | 状态 |
|---|---|:--:|:--:|:--:|:--:|---|
| A2 | 双顶层窗口(现状) | ✅ | ✅ | ❌ | 满帧 · CPU 3% | **已验证可行(在产)** |
| B | render API → 纹理 | ✅ | ❌ | ✅ | 满帧 · CPU ~12% | **已实测可用** |
| D | DirectComposition 视觉合成 | ✅ | ✅ | ✅ | — | **libmpv 做不到,见下** |

#### 方案 D 已排除:libmpv 给不出可被外部合成的 swapchain

原设想:mpv 用 `gpu-api=d3d11` 渲进它自己的 swapchain(零拷贝完整),
Avalonia 走 `WinUIComposition`,两个 visual 放进同一棵 DirectComposition 树。

**实测排除。** 逐个探选项名:

```
d3d11-composition        -> option not found      <-- 不存在
d3d11-composition-size   -> OK                    <-- 只有这个,不足以启用
gpu-context=angle        -> 值合法,但初始化失败(libmpv 旁边没有 ANGLE 的 DLL)
gpu-context=dxinterop    -> 可用,但仍是 d3d11va-copy
```

根本原因是 **libmpv 的公开 API 没有任何途径把它的 swapchain 交出来**:
render API 只有 `OPENGL` 与 `SW` 两种类型,`vo=gpu` 系列则自己拥有 HWND 并自己呈现。

> **顺带澄清一个名字上的误会:** Avalonia 的 `WinUIComposition` **不是 WinUI**。
> 它是 Win32 后端的一个**呈现模式**,底层用 `Windows.UI.Composition`(DirectComposition 的现代版),
> 属于**操作系统合成器 API**,不是 UI 框架 —— Chrome / Edge / Firefox 都在用它做视频覆盖层。
> UI 仍然 100% 是 Avalonia。Avalonia 同族还有个更直白的取值就叫 `DirectComposition`。
> **选路径 B 或 A2 都不需要碰 WinUI。**

### 5.3 Linux 侧结论不同,不要照搬

Windows 的问题根源是「mpv 移除了 ANGLE,render API 没有 D3D11 类型」。
Linux 上没有这个问题:**`vaapi` 与 `nvdec` 都有成熟的 GL 互操作**,
路径 B 在 Linux 上有机会是完整零拷贝的。

**必须单独实测,不许拿 Windows 的结论替 Linux 签字。**

### 5.4 建议

**选路径 B。** 理由:

1. **它消灭的是最痛的那一类 bug** —— 几何对齐(全屏白边 / z 序漂移 / wndproc 重入 / DPI)
   在现有代码里是一整套约 1500 行的窗口管理,也是历史故障的高发区
2. **实测够用**:核显上 1080p60 满帧、4K24 满帧
3. **代价是 CPU 不是可用性**:4K24 从 3% 涨到约 12%
4. **A2 永远是保底**:它与 UI 框架无关,真要退回去,坑全部记录在 `docs/lessons/` 里

**不选的前提**:如果做过实机验证发现低端机型(如四核无风扇迷你主机)在 4K24 下
CPU 余量不够,那就退 A2。**这条要在阶段 1 出口前用真机验一次,别靠估计。**

## 7. 本次实验自己踩的坑(五个,全部导致过错误结论)

**这一轮里我自己的测试台出了五次问题,其中两次让我写出并提交了错误结论。**
列在这里给下一个重跑的人,也给我自己。

1. **两条路径的输出分辨率没对齐。** 第一版路径 A 的窗口 960×540、路径 B 渲 1920×1080,
   B 多做 4 倍像素 —— 那组数据作废。
2. **对离屏窗口每帧 `eglSwapBuffers`。** 窗口摆在 -3000 的屏幕外,每帧对一个 1920×1080
   的离屏 surface 做 swap,**那一步才是瓶颈**(4K 只剩 12 fps)。
   改成渲进纹理 FBO、完全不 swap 之后立刻正常。
   → **这个错误让我提交了「核显上路径 B 的 4K 播不了」这个错误结论。**
3. **开了 `ADVANCED_CONTROL=1` 却从不调 `mpv_render_context_report_swap()`。**
   mpv 因此不知道帧何时上屏,帧率控制整个是瞎的。补上之后 1080p60 才达成满帧 60.0 fps。
4. **同一进程里连开多个 GL 上下文 + 多个 mpv render context 会卡死**(实测 400 秒不返回)。
   必须一次一个后端、分进程跑。
5. **拿"源文件名的字符串命中数"当证据。** 我用二进制里 `d3d11egl` 0 次命中
   推出「现代 mpv 移除了 ANGLE」,而 `gpu-context=angle` 明明是合法取值。
   → **这个错误让我把根因写错了一版。** 选项探测比扫字符串可靠得多。

另外两个没造成错误结论但值得记:

6. **请求 GLES 2 上下文没生效**(传了 `EGL_CONTEXT_CLIENT_VERSION=2`,ANGLE 仍报 ES 3.0)。
   所以「GLES2 是不是当年 Flutter PGS 不显示的真凶」**本次没测到**。
7. **测性能前必须先回读跑在哪块 GPU 上。** 本次全程核显(这次是刻意的),
   但机器有 5060 —— 不看一眼就会把核显数据当成典型值。

> **共同的教训:性能测试里,「测试台本身是不是瓶颈」必须先证伪。**
> 判别器是现成的:同一个 libmpv 用它自己的 VO 跑一遍,如果它快而我们慢,
> 那慢的是我们的循环,不是架构。这一轮我用了三次才想起来用这个判别器。
