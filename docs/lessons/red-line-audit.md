# 红线审计 · 仓库内真实地址泄漏

> 2026-08-30 首次审计。**本文只记位置与类别,不重复泄漏的值本身** —— 把它们汇总到一处
> 等于再泄一次,还更好找。具体是哪几个地址,问项目负责人。

## 红线原文

> **任何 IP、域名、线路/中转地址、端口、账号、密码、密钥、token,都不得出现在任何提交里。**
> 包括代码、配置、注释、文档、README、commit message、issue、PR。
> 私有仓库同样适用 —— 仓库可能改公开、被 fork、被协作者拉取、被 CI 缓存。
>
> 如果已经推上去了:**改写历史或删库重建**,光删最新一版没用。

## 审计结果

**状态:🔴 未整改。** 2026-08-30 扫描全部已跟踪文件,发现 4 类泄漏。

| 类别 | 处数 | 主要位置 | 严重度 |
|---|---:|---|---|
| **A. 线路 / 中转地址** | 9 | `crates/core/src/server_batch.rs:19,21,23,455,457,459,472,473,479` | 🔴 最高 |
| **B. 测试服务器地址** | ~51 | `crates/core/src/emby.rs`(多处注释)、`crates/core/src/net/prefetch.rs:2198`、`apps/desktop/src/lib.rs:1564`、`README.md`、`ui/mobile/README.md:340` | 🟠 高 |

| **D. 公共 DNS IP** | 1 | `crates/core/src/net/cf/` | 🟢 低 |

### A. 线路 / 中转地址(最严重)

`server_batch.rs` 里**不是注释,是测试夹具**:批量解析功能的单元测试直接用了真实的
CDN 线路与弹幕中转地址作为输入样本,并在断言里再写一遍。

这是红线原文点名的「线路/中转地址」。测试夹具里的值会被 `cargo test` 打印、被 CI 日志留存、
被任何 fork 拿到。

**整改:** 换成占位符(`https://cdn.example.com:443` 之类)。
注意 `batch_parse` 的解析逻辑对格式敏感,换值时要保证仍覆盖原来的解析分支。

### B. 测试服务器地址

主要在 `emby.rs` 的注释里,形如「实测 <某台服务器>(Emby 4.9.3)省略 Limit 只返 20 条」。

**这些注释本身是高价值知识** —— 它们记录了「哪个 fork 有什么怪癖」,是不能删的。
整改方式**不是删注释**,而是把服务器换成中性代号:

```
实测 <某台服务器>(Emby 4.9.3)…    →    实测 服务端A(Emby 4.9.3 UHD fork)…
在 <另一台>(4.9.5,接近原版)上…    →    在 服务端B(4.9.5,接近原版)上…
```

代号与真实地址的对照表放在**不进版本控制**的文件里。

> `scripts/extract-lore.py` 已经实现了这套映射(`NICKNAMES` 常量),
> 整改源码时可以直接复用它的替换规则。

### C. 自有公开资产(需要负责人裁决)

项目官网、oauth 代理的 CNAME、README 里的下载/文档链接。

这类**本来就是要给用户看的公开地址**,与「线路/中转」性质不同。
但红线原文写的是「任何域名」,所以需要负责人明确:**公开发布用的自有域名是否豁免。**

裁决之后把结论写进 `AGENTS.md` §3.1,免得下次又要重新判断一遍。

### D. 公共 DNS IP

`net/cf/` 里用公共 DNS 做连通性探测。注释里提到「上一版只打一个目标,一失手整个功能就消失」
—— 这条知识要留。IP 本身是全球公开的匿名 DNS,风险极低,但按字面读仍属「IP」。

同 C,等负责人裁决。

## 已做的止损

- `scripts/extract-lore.py` 生成 `docs/code-lore.md`(源码注释汇编)时**强制脱敏**:
  非白名单主机名 / 非公开 IP / 内部代号一律替换。
  验证:敏感残留 0 处,55 处替换,技术词零误伤
- 白名单只放公开厂商 API、公开文档站、占位符域名

**止损 ≠ 整改。** 源码里的值还在,git 历史里的值也还在。

## 整改路径

1. **先定 C 类的豁免范围**(负责人裁决)——这决定了整改面有多大
2. **改当前版本**:A 类换占位符,B 类换代号
3. **加门禁**:推之前自动扫描,命中即拒。可以复用 `extract-lore.py` 的白名单
4. **处理历史**:红线原文要求「改写历史或删库重建」。
   这是破坏性操作且影响所有协作者,必须负责人决定,不能由 agent 自行执行
